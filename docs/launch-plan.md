# Lumio Browser: Chrome parity and launch plan

From the 2026-10-04 audit (6 agents): Lumio vs 273 Chrome features. Checked boxes are done.

## Batches

### 1. Launch blockers and page-safety basics
_These are correctness, security and licensing issues every user can hit on day one (silent data loss on close, dead mailto/Zoom links, no way past a bad certificate, spam popups, hanging popup permissions, Netflix failing). They are mostly main-process handlers with small new overlay kinds, testable in e2e with local fixtures (beforeunload page, self-signed HTTPS server, 401 endpoint, window.open spam page). Swapping to castlabs Electron changes the runtime every later batch is tested on, so it goes first. New IPC channels must be whitelisted in preload/shell.js (INVOKE/SEND/EVENTS) and preload/dist rebuilt via scripts/build-preload.mjs. Any new overlay kinds should use CSS tokens from the start, because Batch 2 themes everything._

- [ ] DRM / Widevine playback (castlabs ECS + EVS VMP signing in build/package.mjs)

### 2. Light / Device theme foundation (white mode)
_White mode is an explicit user requirement, and it is a cross-cutting refactor of ~300 hard-coded colors that every later batch's new UI (bubbles, tab groups, ⋮ menu, side panel, settings pages) would otherwise multiply. Doing it second means later surfaces are built themeable once instead of re-themed. Set nativeTheme.themeSource so menus, prefers-color-scheme and the PDF viewer follow. Use a :root[data-theme] selector, and watch the existing data-theme attribute on the profile swatches (settings.js:107). Test by snapshotting the shell and each lumio:// page in light, dark and incognito (global.lumio.snapshot, main.js:1424)._

- [ ] White / light mode + 'Device' (follow system) theme mode
- [ ] Tokenize shell.css, overlay.css, aura.css, pages.css and every page CSS; remove hard-coded colors in newtab.js MARK svg, settings.js, welcome.js, panel UI

### 4. Organize and find: omnibox, bookmarks, tab groups, reading list, side panel
_These are data-model features that share storage and sync work. The bookmark tree migration (store.js flat list :218-269, applySyncedBookmarks, importers, export) and tab groups (tab model + session + sync) are the riskiest schema changes, so they ship together with migration tests (tests/store.test.mjs, sync-engine.test.mjs) and one sync adapter pass. The omnibox work is pure functions in omnibox.js with existing unit tests (tests/omnibox.test.mjs). New internal pages (e.g. lumio://sidepanel) need PAGE_HOSTS (protocol.js:21), ALL_PAGES (main.js:690) and the chrome:// alias regex (omnibox.js:17)._

### 6. Motion system and UI polish (best-in-class animations)
_Polish goes after the new surfaces from Batches 1-5 exist, so one motion system (shared --spring easing, transform/opacity only, reduced-motion everywhere) covers all of them instead of being retrofitted piecemeal. It is a separate batch because it mostly touches shell.css, shell.js, overlay.css and overlay.js plus window.js hideOverlay, which needs an exit animation before removeChildView (window.js:154-162). WebContentsViews can't be CSS-animated, so animate the shell around them. Verify with screen recordings at 120Hz, the reduced-motion emulation and a frame-time budget in the shell tests._

## Not possible exactly (Google-only), and what Lumio does instead

- **Cast tab / screen / media to Chromecast and Google TV**: Chrome's Media Router and Cast stack and the Presentation API are not in Electron, and Cast receivers expect Google's sender framework. → Leave Cast out at launch. Later, offer a castv2 library for plain media URLs only, or point Mac users to AirPlay screen mirroring.
- **Web Push notifications when the tab is closed (pushManager.subscribe)**: Chrome delivers push through Google's FCM/GCM. Electron has no push service, so subscribe() fails. → Notifications from open tabs still work. Pinned tabs, background mode with a tray icon, and the Lumio companion push for Lumio's own events. List it as a known limitation.
- **Website speech recognition (webkitSpeechRecognition)**: Chrome streams the audio to Google's speech servers, which Electron can't use. → Polyfill webkitSpeechRecognition in the main world with Lumio's own STT (renderer/ui/voice.js pipeline).
- **Google account browser sign-in and Chrome Sync**: Google's sync and sign-in endpoints are only for Chrome. → Lumio account plus Lumio Sync with end-to-end encryption (already built).
- **Safe Browsing Enhanced protection (and free commercial use of Google Safe Browsing)**: Enhanced protection is Google-only, and the free Safe Browsing API is for non-commercial use. → Paid Google Web Risk API through the Lumio Worker, or open blocklists (URLhaus, OpenPhish, PhishTank) with Lumio's own interstitial.
- **Google Lens (overlay and region search)**: There's no official Lens API, and region uploads use private endpoints. → Open lens.google.com/uploadbyurl for public image URLs, and add 'Ask Lumio about this' on a region screenshot with Lumio's AI vision.
- **Chrome's built-in Translate (Google service or on-device model)**: The translate infrastructure and models are in the Chrome layer and use Google's service. → Lumio translation through the Worker (LLM, or DeepL/Cloud Translate with Lumio's own key) injected into DOM text nodes.
- **Gemini in Chrome and Gemini Nano on-device features (scam detection, Help me write on-device)**: Gemini Nano and the Chrome AI integration are not shipped in Electron. → Lumio AI (already the assistant), with server-side checks only if the user opts in.
- **Live Caption with Google's SODA model**: The SODA speech model is a Google component downloaded only by Chrome. → Capture tab audio and caption it with Lumio's STT or a local Whisper model.
- **Enhanced spell check (Google cloud grammar)**: It is a Google-only service. → LanguageTool or Lumio AI 'Fix grammar and spelling' (already in the selection menu).
- **Google Pay, virtual cards and Chrome's Payment Request sheet**: The Payment Request UI is in the Chrome layer and Google Pay card provisioning is Google's. → Sites fall back to their own or pop-up checkout. Lumio's own encrypted card autofill, later.
- **Extension native messaging (1Password, Bitwarden, Grammarly desktop integration)**: Electron doesn't implement chrome.runtime.connectNative. → Password extensions in standalone mode, and Lumio's built-in password manager.
- **Privacy Sandbox ad APIs (Topics, Protected Audience, ad measurement)**: These are Google ad features, not meaningful outside Chrome. → Turn the APIs off and say so in Privacy settings.
- **Family Link supervised profiles**: Family Link is Google-only. → An optional enterprise JSON policy file for managed installs, post-launch.
- **Google Doodles and the Google-account New Tab Page**: Google content and services. → Lumio's own NTP with backgrounds, shortcuts and AI cards.
- **Chrome's natural read-aloud voices**: Those voices are Google's cloud or on-device models. → System speechSynthesis voices or Lumio TTS.
- **Hybrid passkeys (sign in with a phone via QR / caBLE)**: Electron doesn't expose Chromium's hybrid WebAuthn transport. → Lumio platform passkeys synced through Lumio Sync, and approvals from the phone companion.
- **FedCM browser account chooser ('Sign in with…')**: The FedCM UI lives in the Chrome layer and is missing in Electron. → Sites fall back to pop-up OAuth, which Lumio's popup handling supports (main/tabs.js:212-225).
- **Rich omnibox answers and entity suggestions from Google's private suggest response**: These come from Google-only suggest fields. → Public suggest endpoints for queries, plus our own calculator/units, weather or dictionary APIs, or Lumio AI answers.
- **Google Shopping price tracking and shared tab groups through Google**: Both depend on Google backends. → Lumio Worker features: AI price watching and shared groups through Lumio Sync, post-launch.
