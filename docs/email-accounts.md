# Email + password accounts: the contract

Lumio accounts can be made with an email address and a password, next to Google and Sign in with Apple. This file is the one contract for three builders working at the same time without talking to each other: **server**, **website** and **iOS**. Build exactly what is written here. If something here turns out to be impossible, keep the HTTP behavior unchanged and explain the problem in your final report. Do not edit this file.

## 0. At a glance

- **Create account:** email + password, then Lumio emails a 6-digit code. Entering the code (with the same password) confirms the email and signs you in. An unconfirmed sign-up is never a `users` row. It waits in `email_codes` for up to 24 hours.
- **Sign in:** email + password. If the account is unconfirmed and the password matches its pending sign-up, the reply is `{ needsCode: true }` and a fresh code is emailed.
- **Forgot password:** email, then a code, then a new password. This signs you in and ends every other session of the account, and its apps' pending sign-in hand-off codes.
- **One account per person:** confirming a code for an email that already belongs to a Google or Apple account adds the password to that account. Google sign-in with the email of a password account reaches that same account.
- **Email-only accounts** store `google_sub = 'email:<users.id>'`, following the `'apple:<sub>'` convention. `accountJson` reports `authMethod: 'email'` for them.
- **Web vs app:** the website gets the normal session cookie and a `next` to go to. The iOS app sends `"client": "app"` and gets `{ token, account }`, like `POST /api/auth/apple`.
- **Email** goes through Resend (`RESEND_API_KEY`, sender `EMAIL_FROM`). Codes are stored as an HMAC keyed with the `CODE_KEY` secret. Without either key, the email routes answer 503 `email_unavailable` (§4). Google and Apple are unaffected.
- **No changes** in `main/`, `renderer/` (Mac browser) or `mobile/` (Expo).

    - `tries`: entries of this code; at 5 it stops working.

## 2. Rules

### Email
- **Normalize:** `email.trim().toLowerCase()`.
- **Valid when** the result is 3–254 characters, matches `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`, and has no control characters.
- **Otherwise:** 400 `invalid_email`.

### Password
- **Prepare:** take the string as typed, never trimmed, and apply `password.normalize('NFC')`.
- **Length:** 8–128, counted as code points (`[...pw].length`). This applies to sign-up and reset; anything else is 400 `invalid_password`. There are no other composition rules.
- **Sign-in** accepts any string. A wrong length is simply a wrong password.

### Password hash
- **Algorithm:** PBKDF2-SHA256 via `crypto.subtle` (`importKey('raw', …, 'PBKDF2')` + `deriveBits`, 256 bits).
- **Salt and iterations:** a new random 16-byte salt per hash, and `PBKDF2_ITERATIONS = 100000`, which is the most Workers allow.
- **Stored format:** `pbkdf2-sha256$100000$<salt base64url, no padding>$<hash base64url, no padding>`.
- **Verify:**
  1. Parse the 4 `$` parts.
  2. Refuse an unknown algorithm or an iteration count outside 1–100000. That counts as a mismatch, not an error.
  3. Derive with the stored salt and iteration count.
  4. Compare in constant time.
- **Upgrade:** after a successful password sign-in, if the stored iteration count is below `PBKDF2_ITERATIONS`, re-hash and save.
- **Unknown emails:** a sign-in for an email with no password row still verifies against a fixed `DUMMY_HASH` constant (same format, of a random password nobody knows), so the timing is the same.
- **Constant-time compare:** add `timingSafeEqual(a: Uint8Array, b: Uint8Array): boolean` to `util.ts`.
  - Use `crypto.subtle.timingSafeEqual` when it exists (Workers).
  - Otherwise use an XOR loop. Node has no `timingSafeEqual`, and tests run on Node.
  - Different lengths return false.
- **CPU:** a request never computes more than two PBKDF2 hashes.

### Codes
- **Generation:** 6 random digits. Use `crypto.getRandomValues(new Uint32Array(1))` with rejection sampling (redraw when ≥ 4294000000), take `% 1000000`, and pad to 6 digits with `padStart(6, '0')`.
- **Storage:** only `code_hash` is stored: HMAC-SHA256 (WebCrypto) keyed with `CODE_KEY` (base64 of 32 random bytes), so someone who can read the table can't work out a code from its hash. A code expires 15 minutes after it was sent.
- **Input:** clients may type spaces or hyphens. The server removes `[\s-]`, then requires `/^\d{6}$/`, otherwise 400 `invalid_code`.
- **Tries** (at most 5 per code), counted atomically before comparing:
  1. Compute the HMAC of what was typed, then run `UPDATE email_codes SET tries = tries + 1 WHERE email = ?1 AND purpose = ?2 AND tries < 5 AND expires_at > ?3 RETURNING code_hash, password_hash` (signup rows also need `created_at > now − 24h`), with `.first()`.
  2. If it returns no row, answer `invalid_code`.
  3. Otherwise compare the HMAC with the returned `code_hash` using `timingSafeEqual`. One statement reads the row, so an email that has a code costs no extra query.
- **New codes:** a new code (sign-up again, resend, forgot again, or a sign-in that needs a code) replaces the row's `code_hash`, sets `tries = 0` and `expires_at = now + 15 min`. Only a new sign-up also replaces `password_hash` and `created_at`.
- **One error for everything:** a wrong code, an expired code, too many tries, no row at all, and (for confirm) a wrong password all give the same 400 `invalid_code`. This means the reply never reveals whether an account or a sign-up exists.

### Rate limits
All limits use `auth_attempts`. Insert the row first, then count rows in the window including it (the crashes.ts pattern, so parallel requests see each other). A request is refused when the count is greater than the limit.

| kind | recorded by | window | per email | per IP | when over |
|---|---|---|---|---|---|
| `send` | every signup, resend and forgot that passed validation, plus a sign-in that would send a code | 1 hour | 5 | 20 | 429 `rate_limited`, `retry-after: 900`, no email sent |
| `mail` | a `send` within its limits above (`email_hash`, empty `ip_hash`); removed again when it is over its own limits, so these count only the sends that went ahead | 24 hours per email, 1 hour for all | 10 a day | all of Lumio: 300 an hour | 429 `rate_limited`, `retry-after: 900`, no email sent; over the hourly cap also logs `lumio email global send cap reached <count>` |
| `signin` | every sign-in that passed validation; deleted when it succeeds or answers `needsCode` | 15 minutes | 10 | 50 | **lockout:** answer exactly like a wrong password (401 `invalid_credentials`) without checking the password |
| `code` | every confirm and reset that passed format checks; deleted when it succeeds | 1 hour | (not counted: the `mail` cap bounds guesses at 10 codes × 5 tries = 50 a day per email, and a per-email limit here would let anyone block a person's code) | 30 | 429 `rate_limited`, `retry-after: 900`, no try used |

- **Clearing locks:** a successful sign-in, confirm or reset deletes every `signin` row for that `email_hash`, which also ends a lockout.
- **No enumeration:** limits count the email string whether or not an account exists, so they reveal nothing about accounts. Forgot records its `mail` row even for an email with no account, so it costs the same either way.
- **Why the `mail` caps:** each code is 5 guesses, and sign-up or a sign-in before confirming can arm a new one, so codes per email need a daily cap. The hourly cap on all of Lumio keeps someone with many network addresses (an IPv6 /48 is 65,536 /64s) from using up Resend's quota or getting `lumio-co.online` blocked; refused sends don't count toward it, so one address going over its own limit can't trip it.
- **Cron cleanup:** add `emailCleanup(env, now = Date.now())` to `scheduled()`. It deletes:
  - `auth_attempts` with `created_at < now − 1h`, except `'mail'` rows, which go at `created_at < now − 24h`;
  - `email_codes` signup rows with `created_at < now − 24h`;
  - `email_codes` reset rows with `expires_at < now`.

## 3. Which account (linking)

**Target row for an email:**

```sql
SELECT * FROM users WHERE email = ?1 AND COALESCE(email_unverified, 0) = 0 ORDER BY (password_hash IS NOT NULL) DESC, created_at LIMIT 1
```

`COALESCE(email_unverified, 0) = 0` (`VERIFIED_EMAIL` in auth.ts) is in every lookup of an account by its email: this target, forgot's check, the sign-in lookup, and Google's link lookup. An account Apple made from an email it hadn't verified is never found by that email, so a sign-up for that email makes an account of its own.

- **Confirm sign-up:**
  - **The target exists and has no password** (a Google or Apple account): set `password_hash` from the pending row. Change nothing else, and don't end any sessions.
  - **The target exists and already has a password:** replace `password_hash` and delete all of its sessions and its pending app hand-off codes (`DELETE FROM app_codes WHERE user_id = ?`, since each could still be traded for a session). This works like a reset, because the code proves the person owns the email.
  - **There is no target:** insert `id = 'u_' + randomHex(12)`, `google_sub = 'email:' + id`, the email, `name` and `picture` NULL, plan `'free'`, `password_hash`, and `created_at`. If that insert fails on `users_password_email` (a race), look up the target again once and apply the rules above.
- **Reset:** set `password_hash` on the target. Without a target the answer is `invalid_code`.
- **Google sign-in (`auth.ts` `googleCallback`):**
  - The second lookup becomes `email = ?1 AND (google_sub LIKE 'apple:%' OR google_sub LIKE 'email:%') AND COALESCE(email_unverified, 0) = 0 ORDER BY (password_hash IS NOT NULL) DESC, created_at LIMIT 1`, and then sets `google_sub = sub` (as today).
  - The profile update must not change the email of a row that has a password: `UPDATE users SET email = CASE WHEN password_hash IS NULL THEN ?2 ELSE email END, name = ?3, picture = ?4 WHERE id = ?1`.
- **Apple sign-in (`apple.ts`):**
  - The email link query gets `ORDER BY (password_hash IS NOT NULL) DESC, created_at`. It already links to password accounts through `apple_sub IS NULL`.
  - `appleOnly` becomes `user.google_sub.startsWith('apple:') && !user.password_hash`, so Apple can no longer change the login email of an account that has a password.
  - A new account from a token whose `email_verified` isn't true gets `email_unverified = 1` (else NULL). An `appleOnly` account follows the token's email and sets `email_unverified` to match it each time.
- **`accountJson`:** `authMethod` is:
  - `'apple'` when `google_sub` starts with `apple:`;
  - `'email'` when it starts with `email:`;
  - `'google'` otherwise.

  `authMethod` describes how the account was made and linked, not the current session. An Apple or Google account that added a password keeps reporting `'apple'` or `'google'`.
- **Never send `password_hash` anywhere.** Add `password_hash?: string | null` to the `User` type. `accountJson` already picks only its own fields.

## 4. HTTP API

All six routes are `POST`, take JSON, and live under `/api/auth/email/`. They are routed in `index.ts`'s public block, after `/api/auth/apple`, before the Origin check and `currentUser`. They ignore any existing session.

### Common to every route, in this order
1. **Origin:** if `!sameOrigin(request)`, answer 403 `forbidden` "Not allowed." The website's fetch sends its own Origin; the iOS app sends none.
2. **Body:** it must be a JSON object, otherwise 400 `invalid_request`.
3. **Client:** `client = body.client === 'app' ? 'app' : 'web'`.
4. **Email:** `email` must be a string, then normalized and validated (§2), otherwise 400 `invalid_email`.

### Success reply when someone gets signed in (confirm, signin, reset)
A new session from `newSession(env, user.id)` (30 days, hashed in D1), built from the re-read user row.

- **`client: 'web'`:** 200 `{ "ok": true, "next": safeNext(body.next), "account": accountJson(user) }`.
  - The header is `set-cookie: sessionCookie(url, token, SESSION_DAYS * 86400)`. Export `sessionCookie` from auth.ts.
  - The body never contains the token.
  - `safeNext` falls back to `/account`.
- **`client: 'app'`:** 200 `{ "token": "<64 hex>", "account": accountJson(user) }`, with no `set-cookie` (the same shape as `/api/auth/apple`).

### Errors
All errors use `fail()` and the body `{ "error": message, "code": code }`. The messages use the curly apostrophe ’.

| status | code | message |
|---|---|---|
| 400 | `invalid_request` | That didn’t work. Try again. |
| 400 | `invalid_email` | Enter a valid email address. |
| 400 | `invalid_password` | Use a password with 8 to 128 characters. |
| 400 | `invalid_code` | That code didn’t work. Check the latest email from Lumio, or send a new code. |
| 401 | `invalid_credentials` | Email or password is incorrect. |
| 403 | `forbidden` | Not allowed. |
| 429 | `rate_limited` | Too many tries. Wait a few minutes and try again. (header `retry-after: 900`) |
| 502 | `email_failed` | Lumio couldn’t send the email. Try again in a minute. |
| 503 | `email_unavailable` | Email sign-in isn’t available yet. Use another way to sign in for now. |
| 500 | `server_error` | Lumio hit a problem. Try again. (existing catch-all) |

"Email unconfigured" means `!env.RESEND_API_KEY || !env.CODE_KEY`. Confirm and reset also answer 503 `email_unavailable` without `CODE_KEY`, after their format checks and before a try is used.

### `POST /api/auth/email/signup`
Request: `{ "email": string, "password": string, "client"?: "web"|"app" }`

1. Run the common checks, then validate the password, otherwise 400 `invalid_password`.
2. If email is unconfigured, answer 503 `email_unavailable`.
3. Record a `send` attempt and apply its limit (429).
4. Hash the password and **await** the sign-up email (§6) with a new code. If it fails, answer 502 `email_failed` and store nothing: a code that wasn't sent is never kept (a sign-up already waiting stays as it was).
5. Upsert `(email, 'signup')` with that code, `tries = 0`, the expiry, `password_hash`, and `created_at = now`.
6. Answer 200 `{ "ok": true }`.

The reply is the same whether or not the email already has an account, because a code is always sent.

### `POST /api/auth/email/confirm`
Request: `{ "email", "code": string, "password": string, "client"?, "next"?: string }`

1. Run the common checks. `password` must be a string (otherwise `invalid_request`), and the code format must be valid (otherwise `invalid_code`). Without `CODE_KEY`, 503.
2. Record a `code` attempt and apply its per-IP limit (429).
3. Count an atomic try on `(email, 'signup')` (§2).
4. Compare the code. Then verify `password` against the row's `password_hash`. Either mismatch answers `invalid_code`.
5. Link the account (§3).
6. Clean up: delete the `email_codes` rows for this email (both purposes), the `signin` attempts for the email, and this `code` attempt.
7. Answer with the success reply.

### `POST /api/auth/email/resend` (sign-up codes only)
Request: `{ "email", "client"? }`

1. Run the common checks.
2. If email is unconfigured, answer 503.
3. Record a `send` attempt and apply its limit (429).
4. If an `(email, 'signup')` row exists with `created_at > now − 24h`, give it a new code and send the sign-up email in `ctx.waitUntil`. Log failures; don't report them.
5. Always answer 200 `{ "ok": true }`.

### `POST /api/auth/email/signin`
Request: `{ "email", "password": string, "client"?, "next"? }`

1. Run the common checks. `password` must be a string, otherwise `invalid_request`.
2. Record a `signin` attempt. If the email count is over 10 or the IP count over 50 in 15 minutes, answer 401 `invalid_credentials` right away.
3. Load `SELECT * FROM users WHERE email = ?1 AND password_hash IS NOT NULL`. Verify the password against it, or against `DUMMY_HASH` when there is no row.
4. **The password matches:**
   - Delete the `signin` rows for the email.
   - Upgrade the hash if needed.
   - Answer with the success reply.
5. **Otherwise, an `(email, 'signup')` row (≤ 24 h) exists and its `password_hash` matches:**
   - If email is unconfigured, answer 503.
   - Record a `send` attempt and apply its limit (429).
   - **Await** the sign-up email with a new code (502 on failure, and the row keeps its old code).
   - Give the row that code.
   - Delete this `signin` attempt.
   - Answer 200 `{ "needsCode": true }` (the same for web and app; no cookie, no token).
6. **Otherwise**, answer 401 `invalid_credentials`.

### `POST /api/auth/email/forgot`
Request: `{ "email", "client"? }`

1. Run the common checks.
2. If email is unconfigured, answer 503.
3. Record a `send` attempt and apply its limit (429).
4. In `ctx.waitUntil`, so the answer doesn't wait for (or reveal) whether the email has an account: run one statement, `INSERT OR REPLACE INTO email_codes (…) SELECT ?1, 'reset', <code hash>, <expiry>, 0, NULL, now WHERE EXISTS (SELECT 1 FROM users WHERE email = ?1 AND COALESCE(email_unverified, 0) = 0)`. When it changed a row, send the reset email; if that fails, delete the row again (`code_hash` still the new one) and log it.
5. Always answer 200 `{ "ok": true }`. This also works for a Google-only or Apple-only account, and gives it a password.

### `POST /api/auth/email/reset`
Request: `{ "email", "code", "password", "client"?, "next"? }`

1. Run the common checks, then check the code format (`invalid_code`) and the password (`invalid_password`). Both happen before a try is used. Without `CODE_KEY`, 503.
2. Record a `code` attempt and apply its per-IP limit (429).
3. Count an atomic try on `(email, 'reset')`, then compare the code (`invalid_code`).
4. Find the target (none: `invalid_code`) and set its `password_hash`.
5. Run `DELETE FROM sessions WHERE user_id = ?` and `DELETE FROM app_codes WHERE user_id = ?` (the apps' pending sign-in hand-off codes, which could each still be traded for a session).
6. Clean up: delete the `email_codes` rows for the email, its `signin` attempts, and this `code` attempt.
7. Answer with the success reply. The new session is made after the delete.

### Not changed
- `GET /api/account`, logout, the app hand-off (`/api/auth/app/finish | session | token`) and Google start all stay as they are.
- `index.ts`'s route list comment gains: `POST /api/auth/email/signup | confirm | resend | signin | forgot | reset (email + password; email-auth.ts)`.

## 6. Emails

**The request:**
- `fetch(env.RESEND_API_URL || 'https://api.resend.com/emails', { method: 'POST', headers: { authorization: 'Bearer ' + env.RESEND_API_KEY, 'content-type': 'application/json' }, body })`.
- Header names are lowercase, in a plain object.
- `body = JSON.stringify({ from: env.EMAIL_FROM || 'Lumio <no-reply@lumio-co.online>', to: [email], subject, text, html })`.
- A non-2xx reply or a network error counts as a failure.

**Content:**
- The only variable is the code (digits). No name, address or link goes in, so nothing needs escaping.
- The plain text contains the code exactly once, and no other run of 6 digits.

### Sign-up (also used for the code a sign-in sends)
Subject: `{code} is your Lumio code`

```
Your Lumio code is {code}

Enter it to confirm your email and finish signing in. It works for 15 minutes.

If you didn’t try to sign up for Lumio, you can ignore this email. Don’t share this code: anyone who has it can sign in to Lumio with your email address.

Lumio
```

### Reset
Subject: `{code} is your Lumio password reset code`

```
Your Lumio password reset code is {code}

Enter it in Lumio to choose a new password. It works for 15 minutes. Saving the new password signs you out of Lumio everywhere else.

If you didn’t ask to reset your password, you can ignore this email. Your password stays the same.

Lumio
```

### HTML (both)
Use the same wording. `{heading}` is the first line without the code ("Your Lumio code is" or "Your Lumio password reset code is"), `{body}` is the middle paragraph, and `{footnote}` is the "If you didn’t…" paragraph.

## 7. Website (`website/public`)

## 8. iOS (`ios/`)

### API calls
- Every call is `app.api.request(.post, "/api/auth/email/<action>", json: body, authenticated: false)`. The body always includes `"client": "app"` and never `next`.
- `authenticated: false` matters: a 401 for a wrong password must never clear a stored session.

### Replies
- **Sign-in reply:** decode `{ token: String?, account: AccountInfo?, needsCode: Bool? }`.
  - `token` and `account` present: call `signedIn(SignInReply)`.
  - `needsCode == true`: go to the code screen.
- **confirm and reset:** decode the existing `SignInReply`.
- **signup, resend, forgot:** `{ ok: true }`, decoded as `EmptyResponse`.

### Errors
- Show them with the existing `show(_:)`, so the text is the server's `error` message. `invalid_credentials` arrives as `.server(status: 401, …)`, and 429 as `.rateLimited`.
- Client-side checks use the same messages as the website (§7). Add "Enter the 6-digit code from the email." as a `SignInFailure`.

### Model (`LumioAccountModel`, same file or an extension in it, to reach the private helpers)
- `Provider` gains `.email`. `signingIn = .email` while any email call runs.
- Methods (all `async`):
  - `emailSignUp(email:password:) -> Bool`
  - `emailConfirm(email:code:password:)`
  - `emailResend(email:) -> Bool`
  - `emailSignIn(email:password:) -> EmailSignInResult` (`.signedIn | .needsCode | .failed`)
  - `emailForgot(email:) -> Bool`
  - `emailReset(email:code:newPassword:)`
- Every method follows the Apple flow's guard, `defer` and `show` pattern. Signing in goes through `signedIn(_:)`, which already clears `appleUserID`.

### Server (`server/test/api.test.mjs`, or a new `server/test/email.test.mjs` with the same fakes)
- **`env`:** add `RESEND_API_KEY: 're_test_key'`, `RESEND_API_URL: 'https://resend.test/emails'`, `EMAIL_FROM: 'Lumio <no-reply@lumio-co.online>'`, and a fake `CODE_KEY` (random base64). Expected `code_hash` values are `createHmac('sha256', Buffer.from(CODE_KEY, 'base64'))` of the `'lumio-code|…'` string.
- **Fetch stub:** add `calls.email = []` and this branch:
  `if (u === 'https://resend.test/emails') { calls.email.push({ headers: opts.headers, body: JSON.parse(opts.body) }); return Response.json({ id: 'em_' + calls.email.length }); }`
- **Reading the code:** `const codeFor = (to) => /\b(\d{6})\b/.exec(calls.email.filter((m) => m.body.to.includes(to)).at(-1).body.text)[1];`
- **IP limits:** pass `headers: { 'cf-connecting-ip': '203.0.113.7' }`. App-style calls use `origin: undefined` and `client: 'app'`.
- **Time:** age rows with SQL, e.g. `UPDATE email_codes SET expires_at = 0` or `UPDATE auth_attempts SET created_at = created_at - 3600000`, or pass `now` to the handlers or `emailCleanup`.
- **Must cover:**
  - **Sign-up and confirm:**
    - signup → `codeFor` → confirm sets the cookie, redirects to `next`, and `authMethod` is `'email'`;
    - `google_sub` is `email:<id>`;
    - the stored hash matches `^pbkdf2-sha256\$100000\$[A-Za-z0-9_-]{22}\$[A-Za-z0-9_-]{43}$`;
    - no `users` row exists before confirm.
  - **Wrong codes:** a wrong code 5 times kills the code; an expired code fails; a wrong password at confirm gives `invalid_code`.
  - **Sign-in:**
    - the right password signs in; a wrong one gives 401 `invalid_credentials`;
    - an unknown email gives the same reply;
    - an unconfirmed sign-up gives `needsCode` and a new email;
    - the 11th failure within 15 minutes is locked even with the right password, and a reset unlocks it.
  - **Linking:**
    - confirming the email of an existing Google user adds the password to that row;
    - a Google sign-in to an `email:` account reaches the same row and keeps its email;
    - Apple links to a password account;
    - Apple and Google don't change the email of a row that has a password.
  - **Reset:** forgot → reset ends the other sessions and signs in. A reset, and a confirm that replaces a password, also end pending app hand-off codes (`/api/auth/app/session` and `/api/auth/app/token` refuse them); adding a password to a Google account doesn't.
  - **Timing:** forgot answers without waiting on the `users` table; a wrong reset code runs the same statements whether or not the email has a reset code.
  - **Unverified Apple emails:** such an account is never the target of confirm, forgot, reset or Google's link lookup.
  - **No enumeration:** forgot and resend for an unknown email answer `{ ok: true }` and send nothing.
  - **Rate limits:** the 6th send per email per hour gives 429 with `retry-after`; the 11th code to an email in a day too (refused sends don't count); and past 300 sends an hour from all of Lumio, with no Resend call (sends one address had refused don't count).
  - **Unconfigured email:** without `RESEND_API_KEY`, signup, resend and forgot answer 503 `email_unavailable`; without `CODE_KEY`, confirm and reset too.
  - **Resend down:** a failed sign-up stores no code; a failed reset email removes its code.
  - **App client:** `client: 'app'` gets `{ token, account }` and no `set-cookie`.
  - **Origin:** a cross-site Origin gets 403.
  - **Deletion:** account deletion removes `email_codes` and `auth_attempts`.
  - **Cleanup:** cron cleanup works.
  - **Schema:** `schema.test.mjs` passes.
- **Baseline:** all of `node --test test/*.test.mjs` in `server/` (79 tests before this work) still passes.
